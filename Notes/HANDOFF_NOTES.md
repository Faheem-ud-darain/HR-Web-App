# DelCargo HR — Handoff Notes (Screen Tracking Feature + HR & Admin Line + Related Fixes)

For any agent picking up work on this repo (`SPARXzeux/HR-Web-App`) after this session. Read this before touching tracking-related code, `db.ts`, the tracker-agent desktop app, or the HR & Admin Line / forwarding feature (section 1a below).

## App context (unchanged, still true)

Next.js + Supabase HR portal for DelCargo Logistics. No API routes — all data access is direct client-side Supabase calls via `@supabase/supabase-js`. **RLS is disabled on every table, deliberately, because the app is in a testing phase** — the user has repeated this instruction multiple times: do not enable RLS, add Supabase Auth, or otherwise touch database security/schema without an explicit go-ahead. When new features need new state, the established pattern is to use the generic `delcargo_store` key-value table (`{key, value}` rows) instead of asking the user to run schema migrations.

## 1. Screen Tracking feature (built this session, end to end)

**What it does:** Lets HR/Admin authorize periodic desktop screenshots for specific remote employees, view/export them, and auto-delete old ones monthly with a warning. Screenshot capture cannot happen from a browser tab alone, so it required a real desktop agent.

**Web side (`src/lib/db.ts`, `src/components/ui/TrackingView.tsx`, `src/app/(dashboard)/{hr,admin}/tracking/page.tsx`, `src/app/(dashboard)/employee/tracker/page.tsx`):**
- `TrackingSettings` — one row per employee (`enabled`, `intervalMinutes`, `excludeFromAutoDelete`, `agentToken`), stored in KV key `hr_tracking_settings_prod_v1` as a single array.
- `Screenshot` — each capture is its **own individual KV row** (`key: screenshot_<id>`), deliberately not one shared array, so concurrent uploads from multiple employees' agents never race.
- `TrackerHeartbeat` — live "is the desktop app actually connected" status, one KV row per employee (`key: tracker_heartbeat_<slug>`), written only by the desktop agent, read-only from the web app. Drives the Connected/Not Connected badges.
- Monthly retention sweep (`checkScreenshotRetention`): warns first, deletes after a grace period, honors an exclude list.
- HR/Admin Screen Tracking page: per-employee toggle/interval/exclude, Setup Agent modal (generates a one-time setup code), Screenshot viewer with week/month export to ZIP, and now a "Device" column showing live connection status.
- Employee-facing self-service (Shift Tracker page): employees can now generate their **own** setup code and download the app without asking HR/Admin — scoped strictly to their own email, never anyone else's.
- **Screen tracking is wired to the manual Start Shift / End Shift buttons** (`employee/page.tsx`): starting a shift sets `enabled: true`, ending it sets `enabled: false`. This is intentional design (explicitly requested), not a bug — if you see a report like "tracking toggle turned off after End Shift," that's correct behavior, not a regression.

**Desktop side (`tracker-agent/agent_gui.py`):**
- A packaged Python/Tkinter GUI app (not the old headless `public/delcargo_tracker_agent.py`, which is kept only as an "advanced" fallback). Built into a standalone `.exe`/`.app` via PyInstaller — employees never install Python.
- Setup flow: paste a one-time setup code (base64 of `{u: supabaseUrl, k: anonKey, t: agentToken}` — see `encode_setup_code`/`decode_setup_code`, must stay in sync with `src/lib/trackerSetup.ts`'s `encodeSetupCode`). Before connecting, it shows the resolved employee email and requires explicit "Is this you?" confirmation (RBAC safeguard against pasting a coworker's code).
- System tray/menu-bar icon (`pystray`) — closing the window (✕) minimizes to tray, it does **not** quit. A one-time notification tells the user where to find it again (OS-specific: Windows system tray vs. Mac menu bar).
- "Start automatically when I log in" — Windows Registry Run key / macOS LaunchAgent.
- **Single-device enforcement:** each install has its own persistent `device_id`. Connecting claims the account's heartbeat row outright (overwrites any previous device). Any other device polling that row notices the mismatch within ~60s, shows "Connected elsewhere," and stops capturing — this is how switching PCs auto-disconnects the old one.
- "Use a Different Setup Code" button on the dashboard lets someone reconnect (new code, or take back a superseded device) without a full Disconnect. Each worker thread is started with its own `cfg`/`stop_event` snapshot (passed as explicit args, not read live off `self`) specifically so an old thread can never keep running stale credentials after switching codes — this was a real bug caught and fixed mid-session, keep this pattern if you touch `_worker_loop`/`_start_worker`.
- **CI build/release:** `.github/workflows/build-tracker-agent.yml` builds Windows + Mac natively (PyInstaller can't cross-compile) on `windows-latest`/`macos-latest` runners, triggered by pushing a tag matching `tracker-agent-v*`. Requires `contents: write` permission on the release job (repo's Settings → Actions → Workflow permissions must also be "Read and write" — this bit HR once already, "Resource not accessible by integration" means check that setting first).
- **Tag numbers are sequential and must be unique** — currently at `tracker-agent-v5`. Don't reuse an old tag number; `git push` will silently no-op ("Everything up-to-date") if the tag already exists remotely.

**RBAC model — be honest about its limits:** Every settings function is scoped by the `email` argument the caller passes, and the desktop agent always gets its `employeeEmail` from the server-side settings row matched by token (never from anything it declares itself) — this prevents *accidental* misuse (wrong code pasted, stale cache, etc.), not deliberate tampering. There is no real auth server; a technically-inclined user could still call these functions from devtools with someone else's email. Don't claim this is a security boundary in any documentation or to the client — it isn't, until Supabase RLS/Auth is turned on (deferred, see above).

## 1a. HR & Admin Line — permanent shared channel + cross-forwarding (built 2026-08-31, separate session from the Screen Tracking work above)

**What it does:** A permanent, real chat channel visible only to HR and Admin (never employee/team_lead) — their own private line to each other — plus a "Forward" action on tickets (including closed ones), announcements, and Team Chat/DM messages that drops a copy of that item into the channel as a distinct card, with an optional note attached. Lets HR/Admin escalate something to each other without burying it inside a ticket reply or a DM that the other side might not be watching.

**Web side (`src/lib/hrData.ts`, `src/app/(dashboard)/admin/hr-admin/page.tsx`, `src/app/(dashboard)/hr/hr-admin/page.tsx`, plus forward UI bolted onto `TicketsView.tsx`, `TeamChatView.tsx`, `admin/page.tsx`, `hr/page.tsx`):**
- Reuses the existing `hr_messages` collection and `TeamChatView` component — there's no new collection or new chat component. The channel is a fixed, well-known `teamId` (`HR_ADMIN_LINE_TEAM_ID = 'hr_admin_line'`, in `hrData.ts`), and `TeamChatView` is handed a single synthetic `{ id: HR_ADMIN_LINE_TEAM_ID, name: 'HR & Admin', members: [] }` team — no real `hr_teams` row backs it, same trick `DirectMessagesView` already uses for `dm_<profileId>` channels.
- New routes `/admin/hr-admin` and `/hr/hr-admin`, new "HR & Admin" item at the top of the Sidebar nav (`Radio` icon), visible to hr/admin only.
- `hrActions.forwardToHrAdminLine(...)` in `hrData.ts` is the **single shared forward mechanism** behind all three trigger points (tickets, announcements, chat/DM messages) — don't reimplement forwarding separately if a fourth source type gets added later, extend this function and its `forwardKind` union instead. It re-uploads the source's attachment (if any) as a real new multipart-FormData attachment rather than just linking to the old one, and notifies the *opposite* role (HR forwards → Admin gets notified, and vice versa) with forward-specific wording.
- `NotificationCategory` gained a 7th value, `'hr_admin_line'`, added the exact same way `'maintenance'` was (see `PROJECT_HISTORY.md` section 12 for that precedent): always-fires, deliberately excluded from `NotificationPrefs`/`DEFAULT_NOTIFICATION_PREFS`. This is intentional — HR and Admin should not be able to silently opt out of their own direct line to each other, the same way nobody can opt out of `'maintenance'` notices. If you see this category has no toggle in Settings, that's correct, not a missing feature.
- `pb_hooks/push_notifications.pb.js` was updated to match: `'hr_admin_line'` added to its `pushableCategories` array, bypasses the per-recipient opt-out filter alongside `'maintenance'`, and got its own `"HR & Admin"` fallback title. **Correcting a stale claim living in a comment in `hrData.ts`** (around the `NotificationCategory`/`'maintenance'` block, dated 2026-08-04): it says `pb_hooks/push_notifications.pb.js` "isn't present in this repo checkout/session" — that was true for one earlier session that genuinely couldn't find the file (a tooling quirk, per `PROJECT_HISTORY.md` section 12), but it is **not true now**. The file exists at that exact path and is editable, and this feature's session edited it directly. Don't let that old comment cost you time re-verifying the file is missing — it isn't. (The comment itself hasn't been corrected in `hrData.ts`; if you're in that file anyway, feel free to fix the wording, but don't go out of your way just for this.)
- **Related fix, not scope creep:** `Notification.category` used to be write-only — every `addNotification(...)` call tagged a row with it, but `toNotification()` never mapped it back out of PocketBase, because nothing client-side had needed to read it before (the opt-out check happens server-side in `pb_hooks/push_notifications.pb.js`, against the raw record). This feature is the first thing that needs to read `category` back client-side (to filter the sidebar dot / mark-as-read logic to just `'hr_admin_line'` rows), so `category?: NotificationCategory` was added to the `Notification` interface and wired into `toNotification`. Flagging this explicitly since it's a real, useful fix that happened as a side effect of this feature, not something this feature "needed" in isolation — future agents grepping for why `category` suddenly started round-tripping should land here.
- `buildNotificationLink` gained two new `kind` values: `'hr_admin'` (resolves to `/hr/hr-admin` or `/admin/hr-admin` depending on the viewer's role — every notification into this channel uses this) and `'announcement'` (no dedicated announcement detail page exists, so this just falls back to the role's dashboard root, same "land on the right screen, not the right scroll position" compromise `'task'` already uses).
- Forward gating: the Forward icon on tickets/announcements/chat messages checks `role === 'hr' || role === 'admin'` **directly**, not the more common `isPrivileged` flag used elsewhere in `TicketsView.tsx` — `isPrivileged` also covers the Technical Team role (support staff on employee/team_lead accounts who get elevated ticket visibility), and Technical Team must NOT get access to HR/Admin's private line. If you're touching forward-gating logic and see `isPrivileged` instead of this direct role check, that's a regression, not a refactor.
- Forwarding a ticket works on **closed** tickets too (deliberately — escalating something after the fact, once it's already resolved, is a real use case), unlike most other ticket actions which are gated on `status !== 'closed'`.
- Forwarded messages render as their own card in `TeamChatView.tsx` — a "Forwarded → Ticket/Announcement/Message" tag, the source's title, the optional note, the re-uploaded attachment if any, and a "View original" pill-button link (`ExternalLink` icon). That link is resolved **client-side at render time**, not stored pre-built — `Message.forwardLink` only holds the source's raw id, because `buildNotificationLink` bakes in a role-specific base path (`/hr/...` vs `/admin/...`) but this channel is read by both roles, so the same stored row needs to resolve to a different URL depending on who's currently looking at it.
- **Card color scheme (redesigned 2026-08-31, same session as the initial build): role-based, not self/other-based, and white-based, not solid-fill.** Both regular HR & Admin Line message bubbles and forward cards are colored by **who sent them** (purple border/accent for Admin, sky border/accent for HR — the same pairing `roleBadgeInfo()` already uses app-wide), computed once as `isAdminSender` and reused consistently for every viewer, unlike Team Chat/DM bubbles which color by `isSelf`/`isAdminSender` and would show the same message differently depending on who's looking at it. Cards are a white background with a single-width colored border (`bg-white border border-{purple|sky}-300`), not the old solid-fill/thick-border treatment, so they read as part of the app rather than a loud banner. This only applies inside the HR & Admin Line — gated behind `isHrAdminLine = activeTeamId === HR_ADMIN_LINE_TEAM_ID` for regular bubbles, and unconditionally for forward cards (which, per `hrActions.forwardToHrAdminLine`, only ever land in this one channel anyway) — Team Chat and DM styling is untouched. The Announcement card (amber) was deliberately left alone: that color marks *content type* app-wide, not sender identity, so it's out of scope here.
- **Forward-card layout fix (same 2026-08-31 session):** forward cards originally rendered full-width, like the Announcement banner, ignoring sender/viewer side entirely. Fixed to sit in the same left/right sender-flow as a regular bubble (own forwards on your right, the other person's on your left, `max-w-[75%]` capped) instead of always stretching to the full width of the thread regardless of content length.

**Don't regress this — deliberately lazy-loaded, do not add a background poll for this channel:** `hr/hr-admin/page.tsx` and `admin/hr-admin/page.tsx` do **NOT** call `useAllMessages()` the way `direct-messages/page.tsx` does for its own sidebar unread dot. `useAllMessages()` polls every row of `hr_messages` on a timer just to compute one boolean, and adding a second one of those polls, running at all times for every hr/admin session regardless of whether they ever open this page, was an explicit performance requirement from the user for this feature — not a nice-to-have. Instead, the Sidebar's unread dot for "HR & Admin" (`hasUnseenHrAdminLineActivity` in `hrData.ts`) is driven off `hr_notifications`, which is already being polled app-wide for TopNav's bell (`useNotifications`) no matter which page is open — checking it for `category === 'hr_admin_line'` rows is free, not a new cost. The channel's *actual* messages only start being polled (`useMessages(HR_ADMIN_LINE_TEAM_ID)` inside `TeamChatView`, already lazy/enabled-gated by `teamId` like every other team chat) once someone actually navigates to `/hr/hr-admin` or `/admin/hr-admin` and the page mounts. If a future change to this page (or to the Sidebar) starts calling `useAllMessages()` or otherwise polls `hr_messages` before the page is opened, that's a regression against this explicit requirement — flag it rather than assuming it's harmless.

**Schema migration: DONE, applied directly, not via the fallback script.** `Message` gained `isForward?`, `forwardKind?`, `forwardLabel?`, `forwardLink?`, `forwardNote?`, mapped in `toMessage()` from five new columns on the existing `hr_messages` collection: `is_forward` (bool), `forward_kind` (text), `forward_label` (text), `forward_link` (text), `forward_note` (text). A fallback script exists at `migration_data/add_forward_fields_to_messages.py` (mirrors `create_messages_collection.py`'s pattern) but was **not** what actually applied this — the user explicitly authorized using their already-authenticated PocketBase admin dashboard session in Chrome for this one change, so the five fields were added directly through the Admin UI (confirmed "Successfully updated collection.", field names verified to match `toMessage()`/`forwardToHrAdminLine()` exactly). This does **not** change the app's standing rule (no DB schema/security changes without explicit go-ahead) — this was that explicit go-ahead, for this field-add only, not a standing exception. Forwarding has since been manually tested end-to-end as both HR and Admin (tickets, closed tickets, announcements, and chat/DM messages) and confirmed working — the empty-forward-card failure mode described in earlier drafts of this note no longer applies.

## 2. Bug patterns fixed this session — don't reintroduce these

- **Case-insensitive email matching:** `localStorage.user_email` is always lowercased at login, but `Profile.email` / `TimesheetEntry.employeeEmail` / `Ticket.employeeEmail` can carry whatever casing HR typed during onboarding. Any exact `===` comparison between these silently fails to match. Fixed in 13+ files this session. **Always compare with `.toLowerCase()` on both sides** when matching against a stored email.
- **Stale local-cache read-modify-write races:** `getInitialData()` reads from `localStorage`, not live Supabase. Functions that do read-modify-write on a whole KV array (like `updateTrackingSettings`) must fetch fresh from Supabase first (see `getTrackingSettingsFresh` in `db.ts` for the pattern), or a tab with a stale cache can silently drop/duplicate data written elsewhere. Apply this pattern to any new KV-array read-modify-write function.
- **Fire-and-forget async writes:** many `db.ts` functions used to call Supabase saves without `await`. All fixed, but if you add a new `db.ts` write function, make sure the whole call chain is `async`/`await`ed.
- **Tkinter gotcha:** widget **constructors** (`tk.Label(..., pady=(0,14))`) do NOT accept tuple padding — only `.pack(pady=(0,14))` does. Passing a tuple to a constructor option throws `_tkinter.TclError: bad screen distance`. Just fixed one instance; if you add new Tkinter widgets in `agent_gui.py`, keep `padx`/`pady` tuples on `.pack()`/`.grid()` only.
- **`react-hooks/set-state-in-effect` / `react-hooks/purity` (eslint, `TeamChatView.tsx`, fixed 2026-08-31):** this repo's eslint config includes the newer React Compiler-era hook rules, which flag two patterns that look fine but aren't: (1) a `useEffect` whose body is *only* `setSomeState(...)` calls keyed off a prop/id change (e.g. resetting filters/composer state when `activeTeamId` changes) — the fix is React's documented "adjust state during render" pattern, not another effect: track the previous id in its own `useState`, and if it doesn't match the current one, call `setPrevId(current)` plus every reset `setX(...)` directly in the render body (guarded by that `if`), no `useEffect` at all. See the consolidated block right after `messageLimit` is declared for the pattern to copy. (2) Calling an impure function like `Date.now()` inside a **named** (non-inline) event-handler function — the rule can't always statically prove such a function only runs from an event, not render, so it can false-positive; a scoped `// eslint-disable-next-line react-hooks/purity` with a one-line reason is the correct fix there, not a rewrite. A third genuinely-effect-worthy case (reading `window.location`/calling `window.history.replaceState` for one-shot deep-link handling) got a scoped `// eslint-disable-next-line react-hooks/set-state-in-effect` instead, since that one *is* synchronizing with an external system (the URL), which is exactly what effects are for — don't "fix" that one by moving it to render time.

## 3. Notifications

Added a "Clear All" button to the notification bell (`TopNav.tsx`), available to every role. Implemented as a **per-user dismissal marker** (`NotificationClearedMap`, KV key `hr_notification_cleared_prod_v1`) — mirrors the existing per-user read-map pattern (`isNotificationRead`/`markNotificationsAsRead`). Clearing never deletes the underlying notification or affects other recipients of a broadcast (`recipientEmail === 'all'`).

## 5. Instructions for staying on path

1. **Never touch the database schema or RLS settings** without the user explicitly saying they're ready for deployment phase. Default to the `delcargo_store` KV pattern for any new persisted state.
2. **Always use case-insensitive email comparisons** anywhere you match against a stored email.
3. **Fetch fresh from Supabase before any read-modify-write on a shared KV array** — don't trust `getInitialData`'s local cache for that.
4. **This environment usually has no working build sandbox** (`mcp__workspace__bash` frequently reports "Workspace unavailable — not enough disk space"). Verify changes by careful manual `Read` review of JSX/brace balance and logic, not by assuming `tsc`/`next build` ran. Flag this limitation to the user rather than claiming a build passed.
5. **Desktop agent releases go through git tags**, not manual file uploads: `git tag tracker-agent-vN && git push origin tracker-agent-vN` where N is the next unused number (currently 5). Check `https://github.com/SPARXzeux/HR-Web-App/releases` for the last-used number first.
6. **Give the user copy-pasteable git commands** after every change instead of trying to run git yourself — there's no working shell in this environment either; the user runs commands locally and reports back.
7. When something looks like a "bug" but is actually a previously-requested design decision (e.g., shift buttons controlling the tracking toggle), say so plainly instead of "fixing" intended behavior.
8. Keep `tracker-agent/agent_gui.py`'s `encode_setup_code`/`decode_setup_code` in sync with `src/lib/trackerSetup.ts` if the setup-code format ever changes — both sides must agree on the JSON shape (`{u, k, t}`) and base64url encoding.
